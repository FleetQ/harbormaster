## Insights

### 1. Solo-velocity scaling pattern is sustainable for finite bursts, not steady state

**Evidence**: 489 commits / 5 days = 97.8/day. Two full sprint arcs
(v21 patch line + v22 async-delegate sprint) compressed into the
window. Today's 0-commit memory-only session is the natural cool-down.

**Recommendation**: Treat the burst as the **peak** of a recurring
pattern, not the baseline. Plan the next week assuming 30-50
commits/day max if continuing on v23. Schedule one explicit
"infrastructure / cool-down" day between sprint lines so the cycle is
deliberate, not exhaustion-driven.

### 2. The "split deferred" debt across 3 templates is now load-bearing

**Evidence**: `routes.py` (3064 LOC) was touched **70 times** in 7
days. `dashboard.html` (3064 LOC) **49 times**. `project_detail.html`
(1964 LOC) **33 times**. All three flagged in v21.0.9 + v22.0.0 retros
as "split deferred to v22 architecture sprint" — which never happened
because v22 went directly into async-delegate features instead.

Every merge into these files compounds the merge surface and slows
future refactors. The longer it sits, the harder it gets.

**Recommendation**: **v23.0.0a1 must be the template/routes split**,
not a feature. Concrete plan from the existing partial pattern
(_partials/) — extract `routes_jobs.py` + `routes_network.py` +
`routes_dispatcher.py` from `routes.py`; split `dashboard.html` into
panel partials. Should run before any new feature touches these
files.

### 3. Documentation discipline matched feature velocity

**Evidence**: 29,058 doc LOC added (29% of total), 24 retro files
written (one per release). The institutional-memory side kept pace
with feature side. v22.0.1 retro captured the
`max_turns_reached` debugging pattern within hours of the production
incident — that's the kind of retro that prevents the next repeat.

**Recommendation**: Keep this. Specifically, retain the rule "one
retro per published version" — it forces a pause + reflection
between rapid ships and produces operator-recoverable artifacts.

### 4. v22.0.1 production failure proves the alpha-by-alpha CI gate works

**Evidence**: First post-GA real-world async-delegate
(`d_855b3149d9d3`, collector3.0 feature work) failed silently at
`max_turns_reached`. Root cause: hardcoded `max_turns=10` inherited
from v1's read-only path. **Discovered, diagnosed, and patched
(v22.0.1) in under 90 minutes**, including session JSONL forensics +
idempotent SQL migration + 4 new tests.

The "ship → catch → fix → re-ship" loop worked exactly as designed.
The 8 CI jobs gated the patch; the verify-ci publish gate gated PyPI.
No yank required.

**Recommendation**: Codify the
`max_turns_reached` debugging pattern in the
`v21.0.3-v21.0.9-patch-arc` lessons section. Add a one-line
"check session JSONL for `attachment.type=max_turns_reached`" to the
incident playbook so the next "silent claude exit" is diagnosed in
minutes, not hours.

### 5. Zero contributors besides solo — vehicle bus factor of 1

**Evidence**: `git shortlog` shows one author for the whole 489-commit
window. All retros + memories + ship messages reflect a single
operator + Claude pair-programming model.

**Recommendation**: If harbormaster matters operationally beyond this
machine, the OSS repo is already public on github.com/FleetQ — the
next step is **explicit contributor onboarding docs**
(`CONTRIBUTING.md` or `docs/operator-guide.md` deepening). Reduces
"what if X happens to me" risk. Not urgent, but the alpha-by-alpha
shipping model is opinionated enough that anyone joining cold would
need clear guidance.
